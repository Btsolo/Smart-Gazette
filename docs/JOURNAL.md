# Smart Gazette — engineering journal

A chronological record of how the extractor and classifier were measured and
improved: what we saw, which options we weighed, what we chose and **why**, and
what the measurement said afterwards. It is written to be studied: each entry
can be read on its own.

Companion documents:
- `CLAUDE.md` — project brief and the numbered **lessons** (1–38), the short form of what this journal explains
- `reports/FINDINGS.md` — per-year numbers (gitignored, regenerated by the tools)
- `reports/EXTRACTOR_REPORT.md` — the extractor / table / category analysis
- `reports/PLAN.md` — the living plan with status

---

## 0. How we worked — the principles behind every decision

1. **Measure before changing code.** Every change starts from a number and ends with a number. If we cannot measure it, we do not claim it.
2. **Three independent witnesses.** pdf-inspector and pdftotext both read the PDF's *text layer*; Tesseract reads the *rendered image*. Two readers of the same layer can share a mistake; the image cannot. A disagreement is a flag to investigate, never a verdict.
3. **A held-out year.** 2025 was measured once (the baseline) and then not looked at while designing fixes. A fix only counts if it also helps 2025. This is the same idea as a test set in machine learning: it stops us tuning rules to quirks of the data we stared at.
4. **One change → one test → one commit**, with the numbers in the commit message.
5. **Check our own tools first.** Several "findings" turned out to be bugs in the measuring tools (section 2.3, 5.2, 7.2). A surprising number gets a sanity check before it gets believed.
6. **Keep Python and Java in sync.** The Python tools are where we experiment; the Java service is production. Every cleaner change is ported and checked for identical output (section 12.4).

## 1. Setting up (29–30 Sep 2026)

**pdf-inspector would not load.** `tools/inspect.js` failed with *Cannot find module*. The package was installed globally, but Node's `require()` does not search global modules.
- Options: set `NODE_PATH`, or install locally. `.gitignore` already listed `tools/node_modules/`, i.e. a local install had been intended.
- Decision: install into `tools/` and **pin version 1.15.0** — the version the earlier 20-gazette baseline used. The registry had 1.25.2, but upgrading would change the extractor underneath the baseline, mixing two changes into one measurement.

**How fast is Tesseract?** One 37-page gazette: 13.6 s/page serial. We then measured parallelism instead of assuming it:

| Setup | s / page |
|---|---|
| 1 process, Tesseract's own threading | 10.6 |
| 1 process, 1 thread | 9.4 |
| 8 processes × 1 thread | **1.44** |

Lesson: Tesseract's internal multi-threading was *slower* than one thread; the win comes from many single-threaded processes. Outputs were byte-identical across settings, so parallelism is safe for measurement.

**A `.gitignore` bug.** Part of it had been written in UTF-16 (PowerShell's `>` writes UTF-16), gluing a rule to garbage so `src/.claude/` was no longer ignored. Fixed by rewriting the fragment as UTF-8. This UTF-16 theme returns in section 4.

## 2. Building the OCR witness (`tools/ocr_check.py`)

### 2.1 Design
OCR every page (cached, resumable), then compare notice numbers from three
sources. Page images go to local temp (not OneDrive) and are deleted after OCR.

### 2.2 First result: a false alarm caused by our own assumption
The first trial showed 49 disagreements on two gazettes. Inspection showed the
headers *were* in pdftotext and OCR text. The bug was ours: we had reused the
cleaner's **longest increasing subsequence (LIS)** rule, which assumes notice
numbers appear in ascending order. That is true for pdf-inspector (it fixes
two-column reading order) but not for pdftotext and Tesseract, which can read
columns out of order. Fix: for those two sources, drop any order assumption and
keep the main *block* of numbers instead. Result: 361/361/361 agreement.

**Lesson:** a rule that is correct for one source can be wrong for another; check what each rule assumes.

### 2.3 Later refinement of the same rule
In 2026 No 137 the notice numbers jump 12299 → 13000 inside one issue (and
continue). Our "main block" rule threw away 13000–13012 as cross-references.
Fix: keep every run of ≥ 3 consecutive numbers, because stray
cross-references come one or two at a time. (Lesson 29.)

### 2.4 Scans and how we detect them
Some PDFs are images with a hidden OCR text layer. A fixed rule ("an image ≥ 1500
pixels") missed a 150-dpi scan (2024 No 95). Fix: judge the image by its
**printed size** (pixels ÷ dpi ≥ an A4 page). Lesson: thresholds in pixels break
when resolution changes; physical size does not.

## 3. What the corpus runs revealed (2022–2026)

Five years, 287 PDFs, ~25,000 notices. Highlights (details in FINDINGS.md):

| Finding | Evidence | Lesson |
|---|---|---|
| Scans are invisible to the pipeline | 3,464 notices in 2022–24 | 18 |
| pdf-inspector garbles some scan layers: every character shifted by 29, digits lost | 2023 No 181 | 18 |
| One-character-per-line output makes the cleaner run for hours | 2024 No 148, 312k lines | 20 |
| A NUL byte or a same-line title hides a notice header | 2023/26/1150, 2026/90/7653 | 21 |
| The "dateline" rule deletes dates of death, then deletes the next year as a page number | ~480 lines/year | 22 |
| Split years and ordinals: `20 21`, `7 thJanuary` | largest probate failure cause | 23 |
| Drop-cap letters land on the wrong word: `a dministration` | | 24 |
| Curly punctuation never normalised; templates expect ASCII | relationship filled 0.4% | 25 |
| Duplicate source files (`No 38 (1).pdf`) | 2022 | 33 |
| Election notices have no category | 2022 deep-dive | 34 |

quadratic on text with no full stops. **Lesson:** when something is slow,
measure *where* before guessing why.

## 4. The corpus report — and the bugs it exposed in the old tools

`tools/corpus_report.py` runs the real cleaner, lock, categoriser and templates
over every notice. Building it exposed three problems in the existing tools:

1. **`proper_nouns.py` was never committed.** The templates imported it and crashed. We added a pass-through placeholder and marked name-quality numbers provisional.
2. **UTF-16-first decoding.** The old tools tried `decode('utf-16')` first. On most UTF-8 files that *succeeds* and returns garbage — the pipeline reported 0 notices. Fix: decode UTF-16 only when a byte-order mark says so. (Lesson 32.)
3. **`audit.py` passes without checking.** It reported `ERRORS: 0` because three of its six checks silently skip (their input paths do not exist here). Still open in the plan.

## 5. Tables (your notice 1305 example)

### 5.1 What we measured
Tables found from Tesseract word boxes; for each, how many rows survive cleaning.
Then **multi-page tables**: a table that reaches the bottom of one page and
resumes at the top of the next without a new notice header (31–55 a year).

### 5.2 Two measurement bugs fixed along the way
- A stray "row" (a signature line) let one table run through the next notice → split runs at every notice header.
- On two-column pages the owning notice's header can sit in the *other* column, so "the nearest header above" picked the wrong owner (2026 No 63) → **decide ownership by content**: the notice that actually contains most of the rows.

### 5.3 What it means for a future table lane
Stitch across pages, drop repeated captions, allow column counts to change
between pages, stop at a header mid-page, assign rows by content. (Lesson 31.)

## 6. Elections (2022 deep-dive, `tools/election_probe.py`)

You chose 2022 because it was an election year. The probe found the election
notices have **no home**: IEBC notices land in Legislation via the `electionsact`
keyword; party notices in Miscellaneous; identical IEBC corrections split
between Corrigenda and Legislation. The **declaration of elected persons** (2022
No 169) is a scan the pipeline cannot read.

A subtle point: `keyword_probability.py` judges keywords against a "truth" rule —
and that rule *also* listed THE ELECTIONS ACT under Legislation. So the keyword's
74% precision was measured against a wrong answer key. **Lesson:** check the
yardstick, not just the thing being measured.

Keyword traps found: the IEBC's full name and "Registrar of Political Parties"
also appear in National Treasury budget tables (73% / 66% precision).

## 7. Which extractor is best? (`tools/extractor_eval.py`)

### 7.1 The test
Same notices, same categoriser and templates — only the text source changes:
pdf-inspector (today), Tesseract, pdftotext.

| | Probate templated | Land templated |
|---|---|---|
| pdf-inspector + cleaner | 47–59% | 70–83% |
| Tesseract | 57–66% | 86–89% |
| pdftotext | 77–81% in 2022–23, **22–24% in 2024–26** | 85–86%, then 52–53% |

### 7.2 Sanity checks before believing it
- Tesseract's number accuracy looked low (89%) — our tokeniser treated `81926–80100` (en dash) and `81926-80100` as different. Fixed → 97%.
- Table rows looked broken for every extractor — pdftotext `-layout` prints both columns on one line. Fixed by finding the column gutter.

### 7.3 What it told us
- pdf-inspector's text loses 1 number in 6 (split years, IDs).
- pdftotext has perfect *words* but its *reading order* breaks on newer PDFs — so it is unsafe as the main extractor, but perfect as a **dictionary** (order does not matter for a dictionary). This idea became fix 2.

## 8. The root cause: we were calling the wrong function

Reading pdf-inspector's type definitions (`index.d.ts`) showed ~20 functions; we
used one, `extractText`. Another, `extractTextWithPositions`, returns **whole
lines with correct words** plus x/y coordinates. The fragmentation was a
property of `extractText`, not of the PDFs.

**Lesson:** before building workarounds for a library's output, read the
library's full API. Several weeks of cleaner rules (lessons 3, 23, 24) treat
symptoms this one call removes at the source.

## 9. Fix 1 — the positions-based extractor (`tools/inspect_positions.js`)

### 9.1 The algorithm
1. Group positioned pieces into lines by baseline (same y within 0.4 × font size).
2. Join pieces on a line with a space only when the real gap is > 0.2 em.
3. Order the page as printed: left column, then right column, with **full-width blocks** (mastheads, wide tables) acting as band breaks.

### 9.2 The ordering problems — an iteration log
Every step was measured on the same gazettes (inversions = headers out of order).

| Attempt | Idea | Result |
|---|---|---|
| v1 | bands split at any line crossing the gutter | 3–7 notices/year lost; the last header on some pages swapped |
| v2 | header stranded below the right column belongs to the full-width block | fixed 2022 No 120 p21 |
| v3 | lines with ≥ 3 pieces = table rows (span the page) | **worse**: small-caps pieces counted as cells, columns interleaved |
| v4 | count wide gaps (> 1.5 em) instead of pieces | better; signature blocks (`MR/3883998   Governor…`) still flagged |
| v5 | require off-margin cells on **both** sides of the gutter | centred headings still caused false rows |
| v6 | require a **run of ≥ 3** such rows | most fixed |
| v7 | a trailing left-column header moves after the right column only if its **notice number** is higher than every right-column header | 2023 No 44 fixed; unbalanced columns protected |
| v8 | full-width rows need **≥ 2 cells each side** | in-column tables beside indented prose no longer misread |

Two ideas did the heavy lifting: **look for evidence over several rows, not one**
(a single line is often a coincidence), and **use domain knowledge** — notice
numbers always ascend within an issue (lesson 14), so they can arbitrate order.

### 9.3 Results
Same templates, cleaner unchanged:

| | Before | After fix 1 |
|---|---|---|
| Probate notices templated | 47–59% | 70–81% |
| Probate blocks templated | 72–83% | 90–93% |
| Numbers intact | 88–92% | 96–98% |
| Table rows complete | 28–46% | 49–70% |
| Notices lost | – | 2 of 15,915 (1 recovered) |
| **Held-out 2025** | probate 53.6% | **75.8%**, 0 lost |

End to end through `pipeline.py` on two 2023 gazettes: notices handled without
an AI call 51.8% → 68.6%. Committed as `75de643`.

## 10. Tesseract vs PaddleOCR (`tools/ocr_compare.py`)

### 10.1 Test design
Ground truth is the hard part for OCR. We used three sets: clean born-digital
pages (truth = text layer), **the same pages artificially degraded** (150 dpi,
JPEG, noise, tilt — truth still exact), and real scans (truth only where a good
hidden layer exists). Degrading pages we already have exact text for gives a
scan test with exact answers.

### 10.2 What happened
- PaddleOCR's own CPU build crashed on this Windows machine (oneDNN error), and without oneDNN it could not finish one page in 20 minutes. Install: 998 MB.
- **RapidOCR** runs the same PaddleOCR models through ONNX Runtime and worked.
- RapidOCR read numbers far better (96–99% vs 75–82% on table pages; robust on degraded scans); equal on prose; ~3× slower using ~3 cores.
- Timings were inflated because Windows Explorer and OneDrive held the CPU at 100% — we compared engines back-to-back on the same pages so the comparison stays fair.

**Decision:** RapidOCR for the scan lane, Tesseract as the fast fallback; no OCR at all for born-digital PDFs (the text layer is exact).

### 12.1 Fix 3 — cleaner (`tools/gazette_clean.py`)
Each change targets one lesson and was unit-tested on a minimal example first:

| Change | Lesson | Test |

| one-char-per-line input → empty → scan lane | 20 | |

Measured: `petitioner_relationship` filled 0.1% → 70–73% (the curly apostrophe).

### 12.2 Fix 2 — vocabulary repair (`tools/vocab_repair.py`)
Re-cut broken words using a dictionary. Two dictionary sources were compared:
per-gazette pdftotext (needs pdftotext in production) and **one corpus
dictionary** built from 2022–2024 (our own material, shipped with the code).
They scored the same on land (85.4%), so the corpus dictionary wins on
simplicity. It is tested on 2025 and 2026, which it was not built from.

The guard rules evolved from failures — each one is a lesson in itself:

| Failure seen | Why it happened | Guard added |
|---|---|---|
| `at Omogonchor` → `a tOm o g on c h or` | initials made single letters "words" | short pieces must be real short words; ≤ 1 extra word |
| `knownas` not split | the broken form itself appears 3× in the corpus | only words seen ≥ 20 times may be used |
| `REGISTRAT ION` → `REGI STRAT ION` | took the first window that worked | try every window, keep the best-evidenced |
| `at Onywere` → `a tOny were`, `in Kenya` → `inKenya` | re-cut through good words | a common word must survive (merges exempt); extra words only if every token is rare; new words must be ≥ 5× more common |
| `JohnDoe` (real case: two glued names) | glued names, no dictionary can know | split at lowercase→Uppercase (not Mc/Mac/De/Van) |

17 regression cases now pass.

### 12.3 Java parity
The same fix-3 changes were ported to `GazetteTextCleaner.java`; a small Java
program compared notice numbers on five gazettes: **identical** to Python.

### 12.4 Integration and Java parity for fix 2
- Python: `pipeline.process()` runs the repair after `clean()` and before the lock.
- Java: `VocabRepair.java` (rule-for-rule port) called from `GazetteTextCleaner.clean()` at the same point; the dictionary ships as `src/main/resources/vocab/gazette_vocab.txt`.
- Parity: the same cleaned text from five gazettes was repaired by both — **byte-identical output** (~2,400 lines changed by the repair).
- `audit.py` now runs the 5 cleaner and 13 repair cases as regression tests (28 behavioural checks, `ERRORS: 0`).

## 13. A bigger dictionary, and a lexicon with meanings (3 Oct 2026)

**Dictionary.** Rebuilt from all five years (born-digital gazettes only — scan
text layers contain letter-spaced fragments such as `G a z et te` that would
pollute it): 36,640 → **64,088 words**. Trade-off, stated honestly: 2025 is now
inside the dictionary, so it is no longer an independent test of the word
repair. The next held-out set will be the new gazettes you add later.

**Lexicon** (`tools/gazette_lexicon.json`). A word-frequency list knows spellings,
not meanings. The lexicon is the "normal dictionary" part: 50 hand-written
entries (probate, land, elections, county government, environment, finance,
abbreviations), each with a plain-English definition, variants and synonyms —
e.g. *L.R. No.* = *Land Reference Number*; *letters of administration
intestate* ≈ *grant of administration*. Plus 35 spelling-variant pairs mined
from the corpus (`tools/build_lexicon.py`): licence/license, judgement/judgment,
programme/program, centre/center…

How the mining was kept honest: the first run produced false pairs — for/four,
or/our (too short), filed/filled (a bad rule), two pairs of Kenyan surnames (personal
names). Fixes: ≥ 5 letters, drop the `-lled` rule, ≥ 6 letters for `-our`.
**Lesson:** automatic rules need a human look at their output before use.

Planned uses: keyword matching through synonyms (fix 6), plain-English
explanations in generated articles, and both spellings counting as words.

## 14. Fix 4 — template gaps (3 Oct 2026)

### 14.1 How the gaps were found
`tools/template_gaps.py` runs the templates on the *current* pipeline text and
groups every rejection by its cause, with examples. Reading the examples before
writing any regex mattered: the largest probate "failure" (377 blocks a year)
was not a probate problem at all.

### 14.2 What was changed, and why

| Gap (2023 + 2025) | Root cause | Fix |
|---|---|---|
| 377 "probate" blocks starting `CAUSE NO. 158 of 2019, has issued grant… land title deed` | **land** notices (title transfer after a death) filed as probate because the body mentions a court | categoriser: a Land Registration/Titles Act **heading** wins over court words in the body (Python `categorise`, Java `keywordPreFilter`) |
| ~280 `grant of probate of written will of X` | template required "of **the** written will" | `RE_ACTION`: "the" optional; also `for grant`, `estate X`, ad litem / colligenda / will annexed / limited grants |
| 278 year-only deaths, 206 with no date | date of death was required | date optional; year kept (`1978`); generator already handles a missing date |
| ~150 other death forms | `died along`, `died in Nairobi, on`, `at X, 6th April` (no "on"), typo `n 3rd` | `RE_DEATH` accepts these |
| 185 blocks cut in two | `(Formerly CAUSE NO. …)` / `(as consolidated with CAUSE NO. …)` split the record | `split_causes()` ignores a cause number quoted inside a parenthesis |
| `advocate_firm` filled 3–5% | most notices omit "advocates": `through Messrs. Magee of Nairobi, for a grant` | `RE_ADVOCATE` ends at `of <Town>, for` / `, for a grant`; searched in the whole block but must start before the action |
| `petitioner_relationship` = "last will" | `the executor named in the deceased's last will` | read "executor" from that phrase |
| 126 land `of that piece` | template required `of all that` | "all" optional |
| 86 land parcels cut to `E` | `E. Bukusu/N. Sangalo/3026` — a full stop after an initial ended the ID | a stop after a single capital is not an end |
| land `title No. X` without "registered under"; `registered as C.R. 9172/1` | rigid prefix; registry number as the only ID | prefix optional; C.R./I.R. as a last resort |
| corrigenda 0% | template required a `CAUSE NO.`; most corrections are appointments, IEBC, NLC | `extract_notice()`: the corrected notice number + `printed as … to read …` or numbered delete/insert instructions; tolerates the source typo "Gazzette" |

### 14.3 A bug caught by testing each piece
The first version made almost every probate notice fail: the new connector
`to the estate (of)` swallowed the space after "of", and the pattern then
demanded another space. One character. Caught in minutes because every regex
change was run on a handful of real examples **before** the scorecard.
**Lesson:** test the smallest piece first; a five-year scorecard is too slow a
way to find a typo.

### 14.4 Regression tests
`audit.py` gained 10 fix-4 cases (each a real failure). 38 behavioural checks,
`ERRORS: 0`.

| Year | Probate notices | Probate blocks | Land | Corrigenda |
|---|---|---|---|---|
| 2022 | 76.0 → **81.1%** | 91.8 → **93.4%** | 86.0 → **91.6%** | 0 → 11% |
| 2023 | 80.8 → **88.1%** | 91.3 → **95.9%** | 85.4 → **94.4%** | 0 → 25% |

Notice detection unchanged (0–1 missed, 0–1 extra per year). The routing fix

## 15. Java and Python — what each is for

The same cleaner and word repair now exist in both languages, verified to give
identical output. Measured on five gazettes (cleaner + repair + lock):

| | Python (`tools/`) | Java (`GazetteTextCleaner`, `VocabRepair`) |
|---|---|---|
| Speed per gazette | ~2.4 s | ~0.9–1.0 s after a ~2 s warm-up |
| Memory | ~2 MB peak allocations | ~24 MB heap |
| Start-up | instant | JVM start + warm-up (~2 s) |
| Where it runs | measurement and experiments | production (Spring Boot service, database, AI calls) |
| Strengths | fast to change and test; rich libraries for analysis (OCR, statistics, regex experiments); the whole measurement toolkit is here | type safety; one deployable service; faster at scale; integrates with the database, scheduler and web UI |
| Weaknesses | not part of the deployed app; no static types (typos found at run time) | slower to iterate (compile, restart); every rule exists twice and must be kept in sync |
| Templates | yes (probate, land, corrigenda) | **not yet** — open item |

**Why both:** experiment and measure in Python, where a rule can be changed and
scored on 25,000 notices in minutes; port a rule to Java only when the numbers
justify it, then prove the two give the same output (parity tests, sections
12.3–12.4). The cost is duplication. The alternative — calling the Python
tools from Java as a subprocess, like `inspect_positions.js` — would remove the
duplication at the price of a Python runtime in production; worth considering
when the templates are moved over.

## 16. Fix 6 — categories (3 Oct 2026)

**What we asked.** Which notices are in the wrong category, or cost an AI call
because no keyword catches them?

**How we measured.** A new scorecard, `tools/category_eval.py`, runs the Python
categoriser and the exact Python port of the Java pre-filter on all 21,250
notices of 2022–2026 and compares both with the notice's **heading** (the Act
and subject line, via `misc_review.RULES`). The heading is the referee because
it is structural and independent of the body keywords being tested (lesson 12).
Cleaned text is cached in `cleaned/` so a rule change is re-scored in about 2
minutes instead of re-cleaning every gazette.

**Baseline.** 2,821 notices (13%) reach the Java AI triage call. The biggest
single group: **558 county notices**. The County_Government schema existed,
but no rule ever sent a notice to it, so Python filed them as Appointments
(233) or Miscellaneous, and Java paid for an AI call on 511 of them.

### 16.1 Step 1 — route County_Government

| | before | after |
|---|---|---|
| notices filed County_Government (Python = Java) | 0 | **634** |
| county-headed notices caught | 0 of 558 | **548** of 558 |
| Java AI triage calls, 2022–2026 | 2,821 | **2,232** (−589, −21%) |
| Python Miscellaneous | 956 | 724 |
| Java vs Python, all 21,250 notices | – | **identical** (parity test) |

**The rule** (`category_census.COUNTY_HEAD`, Java `CategoryRules`). It reads the
first 400 characters and is **case-sensitive**. It fires on any of:
- THE COUNTY GOVERNMENTS ACT (and its typo "CUNTY");
- URBAN AREAS AND CITIES;
- COUNTY ASSEMBLY OF X, or X COUNTY ASSEMBLY STANDING ORDERS;
- COUNTY GOVERNMENT OF X;
- a county's own Act (THE KIAMBU COUNTY FINANCE ACT).

**Why case-sensitive.** A county heading is printed in capitals. National
notices mention "the County Assembly of …" only in their body, and a
case-insensitive rule would steal them.

**What we decided, and why.**
- **Where it runs.** Directly after Corrigenda and Change of Name, before every
  body keyword. County notices contain "appointment", "licence" and "tender" in
  their bodies, and those keywords used to win.
- **Planning stays Land_Property.** 58 notices read "COUNTY GOVERNMENT OF X —
  completion of a physical development plan". Their subject is land; the county
  is only the issuer, and the county name is still a field in the record.
- **Not counties.** Parliament's notices (THE SENATE / NATIONAL ASSEMBLY
  STANDING ORDERS) are left out, as are probate and Elections Act notices.
- **The last 10 "misses" are correct by design:** planning notices, Parliament,
  and one corrigendum.

**Lesson 39:** a category nobody routes to is invisible. The schema existed
for months while hundreds of notices a year paid for an AI call. Count where
each category's notices actually come from, not just whether the schema exists.

**Regression cases:** six routing cases in `audit.py`, including a body
mention that must not count, planning that stays land, and the Senate.

**Java:** `CategoryRules.isCountyHeading` is a separate class, so the parity
test can call it without starting Spring. It is called from `keywordPreFilter`.
County_Government was added to the AI triage list and the categories page.
**Deployment note:** `schemas/field/county_government.json` exists only in
your working copy (never committed). A deployed build without it saves a
county notice as a "Schema file not found" fallback, so commit the schema
before deploying.

## 17. The laws a notice cites — Constitution and County Governments Act (3 Oct 2026)

**Your idea.** When a notice says "IN EXERCISE of the powers conferred by
Article 179 (2) (b) of the Constitution", the reader should be able to read
Article 179 (2) right there, beside the notice and the AI article.

**Measured first** (`tools/citation_census.py`):
- The Constitution is cited by article in 289 notices (1.4% of all). That
  rises to **24% of county notices**.
- The most-cited articles are the devolution ones: 179 (county executive
  committees), 184 (urban areas), 183, 235 (county staff), 187 and 186.
- Top of all is Article 88 (the IEBC), in 50 notices.
- **Counties have no constitutions of their own.** They work under Chapter
  Eleven of the national Constitution and the national County Governments Act
  (cited in 231 county notices), plus their own county Acts.

**What we built.**
1. **`tools/build_law_reference.py`** converts the official Kenya Law pages
   (Akoma Ntoso HTML, saved in the gitignored `raw/law/`) into
   `src/main/resources/reference/constitution.json` and
   `county_governments_act.json`, beside `geography.json`.
   - **Constitution:** all 264 Articles, 18 Chapters, 54 Parts and 6
     Schedules, version 2010-09-03.
   - **County Governments Act:** 157 sections, 15 Parts and 3 Schedules,
     consolidated to 2022-12-31.
   - **Each provision** is stored with its number, title, chapter or part, full
     text, and sub-articles, keyed by number for direct lookup.
   - **Copyright:** Kenyan written law is not subject to copyright, so it can
     ship with the app.
2. **`tools/law_refs.py`** finds the citations in a notice and resolves them:
   - "Article 179 (2) (b)" → Article 179, sub-article (2);
   - "Articles 88 (4), 97 (1) (a) and 194" → three articles;
   - "section 30 (2) (f) of the County Governments Act" → section 30;
   - "Fourth Schedule to the Constitution" → that schedule.

   A citation of an Act we don't hold yet is still listed, marked "not in
   Smart Gazette yet". The coverage report names the next law to add, ordered
   by how often notices cite it.
3. **Java `LawReferenceService` and a "Laws Cited (N)" tab** on the notice
   page. Each provision opens to its text; a sub-article citation shows just
   that sub-article with its lettered paragraphs. Citations are found when the
   page is viewed, from the stored notice text, so the database doesn't change.

**Results.**

| | |
|---|---|
| notices citing a provision (any law) | 1,590 |
| … resolved to text we hold | 398 |
| county notices citing a provision | 361, of which **267 (74%)** resolved |
| Constitution citations whose article exists | all 463 |
| Java vs Python, 21,250 notices / 2,277 citations | **identical**; ~0.2 ms per notice |
| spot check, 14 random resolved citations against their context | 14 correct |

**Laws to add next, by citations:** Land Act 165, Water Act 110, Universities
Act 92, Companies Act 85, Mental Health Act 66, Political Parties Act 64,
Elections Act 59. For the remaining county notices: the Urban Areas and Cities
Act and the Public Finance Management Act. Each one is a single
`build_law_reference.py` run, plus one line in `LAW_NAMES` (Python and Java).

**Design choices, and why.**
- **One JSON per law, keyed by provision number.** A citation is a direct
  lookup: no search, no AI call.
- **Text kept exactly as published.** A legal provision must not be
  paraphrased; the AI article can explain it, but the quoted text is the law.
- **Citation rules.** An "Article" must point at the Constitution
  ("Article 5 of the Treaty" is skipped). A "section … of the Constitution"
  (a Sixth Schedule paragraph) is skipped rather than guessed.

**Lesson 40:** reference data turns a notice from a claim into something
checkable. Measure which references matter (24% of county notices, devolution
articles first), then hold the source text exactly and resolve it by key.

**Regression cases:** seven citation cases in `audit.py`.

## 18. Fix 5 — the scan lane (3 Oct 2026)

**The problem.** 21 of 287 gazettes (2022–2025) are scans, and 2 more are
mixed. Their text layer is missing (Foxit, PFU) or a hidden OCR guess
(OmniPage), so pdf-inspector finds **0–1 notices** in each. That is about
**3,800 notices the system could not see**: 1,272 pages of probate cause
lists, land notices and election results.

### 18.1 Step 1 — Tesseract + OCR repair + the normal cleaner

`tools/scan_lane.py` is the Python reference; Java has `ScanLaneService` and
`OcrTextFixer`.

1. **Detect.** A page is a scan when it carries a raster image of at least
   about A4 in **printed** size (pdfimages: pixels ÷ ppi). A gazette is a scan
   when at least half its pages are. In the corpus the split is clean: every
   scan has an image on every page, and no born-digital issue has one.
2. **Read.** Tesseract at 300 dpi, one single-threaded process per page in
   parallel (`OMP_THREAD_LIMIT=1`, measured fastest).
3. **Repair the OCR** (new), page by page:
   - notice headers as OCR prints them ("GAZETTE N0TICE No, 8O6O" → "GAZETTE
     NOTICE NO. 8060"), at line start only, never "… No. 123 of 2024";
   - "CAUSE NO. E139 **oF** 2022" → OF. One character, and it alone failed
     **1,600** cause blocks;
   - specks: a quote before a word ("'By"), a colon or dot inside a sentence
     ("for a: grant", "who. died"), "! 5th" / "| 1th" (1), "Sth" (5);
   - **word correction from our own dictionary**: a word never seen in five
     years of born-digital text, which **one** known OCR confusion (t↔f, l↔s,
     rn↔m, li↔h, � = any letter …) turns into a clearly more common Gazette
     word. For example "tor"→for, "shail"→shall, "Keriya"→Kenya,
     "Otierio"→Otieno.
4. **Then the normal pipeline**: cleaner, vocabulary repair, ascending lock.
   Categoriser and templates are unchanged.

**The correction was reviewed, then narrowed.** The first version made 787
corrections and changed **real names and words**: Shaw→Show, Mboga→Mbogo,
Saita→Soita, laid→said, Hay→Bay. Three rules were added:
- a word seen in born-digital text is real (a capitalised word: seen even
  once; a lowercase word: more than 3 times);
- a capitalised word (usually a name) may only become a very common word
  (≥2,000 uses);
- 3-letter words may only become function words (for, on, the …).

The a↔o swap was dropped. That leaves 293 corrections, and every one in the
review was a real OCR error. **Lesson 42:** an automatic corrector must be
judged by reading its corrections. Changing a correct name is worse than
leaving an OCR error, because the notice is already flagged as OCR.

**Results** (23 scanned / mixed gazettes, 1,272 pages):

| | text layer (before) | scan lane |
|---|---|---|
| notices found | ~0 | **3,718 of 3,796 (97.9%)**, 38 extra |
| probate cause blocks templated | 0 | 78.0% → (OCR repair) **86.6%** |
| probate notices fully templated | 0 | 54.4% → **68.3%** |
| land notices templated | 0 | **79.5%** |

Born-digital is 93–97% for blocks and 92–94% for land; the gap is OCR noise.
Three "1-notice" scans are correct: each is one notice built around a huge
table (company register, land-parcel schedule, petroleum basin blocks). Those
need the table lane (fix 7).

**Java parity.**
- `OcrTextFixer` vs Python on all 1,272 pages: **identical** (about 11 ms per
  page).
- End to end on 2024 No 95 (52 pages: Java detection → Tesseract → repair →
  Java cleaner): **the same 208 notices**, text identical to Python except
  one trailing newline.

**Lower confidence is shown, not hidden.** Every notice now records
`extraction_source` (`text-layer` or `ocr-tesseract`; a new nullable column,
`ddl-auto=update`). The notice page shows "Read from a scanned copy … check
names and numbers against the original PDF" for OCR notices.

**Deployment needs** `tesseract` and the poppler tools (`pdfimages`,
`pdftoppm`) installed (in Docker: `apt-get install tesseract-ocr
poppler-utils`). Settings: `extraction.scan.*` (enabled, workers, paths, dpi).
If they are missing, the scan check fails soft and the text layer is used.

**Regression cases:** 8 OCR-repair cases in `audit.py`, including the
cross-reference that must not become a header, a name that must survive, and
O'Brien.

### 18.2 Step 2 — a second OCR engine, or a better first one?

**First, a better yardstick.** "97.9% of notices found" in step 1 was
measured against the headers **Tesseract itself** saw, so it could not reveal
headers Tesseract missed. Inside one issue notice numbers run consecutively,
so the slots from the first to the last number count the notices actually
printed, independently of any engine. Against that count, Tesseract found
**94.2%**, and the land issues were much worse (2022 No 231: 76%, No 238: 78%).
**Lesson 43:** never score a reader with its own output. Find a referee it
cannot influence; here, the consecutive numbering.

**Then the obvious fix: RapidOCR.** It found many of the missing headers, but
it costs about 25 s a page against Tesseract's 2.5 s, plus a second runtime
in production. So it was only run where it is needed: the pages around a gap
in the numbering, 178 of 1,085 (16%). Its notices replaced Tesseract's inside
each gap. Result: 94.2% → 97.5%.

**Your question: can we improve Tesseract instead?** The column-split second
pass (each column read alone in single-column mode) recovered only 29 notices
against RapidOCR's 131. So I looked at **what Tesseract printed where a header
was "missing"**. It had read almost every one, but garbled: "GAZETTR NOTICE
NO 13318", "GAZETTE NOTICENO 13321", "GAZETTE Nomice No 13342". The header
pattern was the problem, not the engine.

**Fuzzy headers.** A header stands alone on its line: letters within 3 edits
of GAZETTENOTICENO, then a 2–6 digit number, and nothing else. No digits are
allowed before the number, because the first version turned "Gazette Notice
No. 123 **of 2024**" into notice 2024. Caught by checking its output.

| | notices found (of 3,984 slots) |
|---|---|
| Tesseract, step 1 | 3,752 (94.2%) |
| + RapidOCR on gap pages | 3,883 (97.5%) |
| Tesseract + fuzzy headers | **3,844 (96.5%)** |
| Tesseract + fuzzy headers + RapidOCR | 3,902 (97.9%) |

**Decision: Tesseract only.** RapidOCR would add 58 notices over four years
of scans (about 15 a year) for a 10× slower second engine in production. The
RapidOCR scripts (`rapid_ocr_pages.py`, `ocr_engine_eval.py`) stay as
measurement tools. **Lesson 44:** before adding a component, look at how the
existing one fails. Here the "missing" data was present and only the pattern
was blind to it.

**Also fixed in this step:**
- **Headers far outside the issue's run** ("(GAZETTE NOTICE NO. 963)" in an
  issue of 9618–9771; a misread "1623382") are lowered to plain text
  (`drop_outliers`; Java `ScanLaneService.dropOutliers`).
- **A real Java/Python difference.** The cleaner's list of complete words
  used for joining lines had one more line in Java (`amend printed read land
  title parcel situate proprietor lost replacement objection`). Python glued
  "land"+"contaiming" and "read"+"Kiambu". Java was right; Python now matches.
  On born-digital text this changes no notice and no category.
- **Land parcel IDs ran on** ("Mombasa BlockXXV/49 situate in Mombasa …",
  "Kisumu/Karateng/1874 and whereas …") when the comma before the next clause
  was missing, which OCR often does and some born-digital notices do too.
  The comma is now optional, "measuring" and "virtue" also end a parcel, and
  OCR's "ttle" is accepted for "title".

| land notices templated | before | after |
|---|---|---|
| born-digital 2023 + 2025 | 93.3% (126 run-on ids) | **93.7%** (35, mostly genuine multi-parcel lists) |
| scans | 76.9% (114 run-on ids) | **85.0%** (19) |

**Scan lane, final:** 96.5% of notices, probate cause blocks 86.7%, land
85.0%, all with Tesseract only. Java `OcrTextFixer` (with fuzzy headers) is
identical to Python on all 1,272 pages.

**Teaching Tesseract (your idea, for later).** Tesseract is open source and
can be fine-tuned (tesstrain) on our own line images. The born-digital pages
give exact labels for free. On real scans, the lines where Tesseract and
RapidOCR **agree** can serve as extra labels (the slow engine teaches the
fast one once, offline). The production system stays one engine. This is in
the plan (Phase 3b, Gazette-trained OCR).

**Regression cases:** 8 more in `audit.py` (fuzzy headers, including the
cross-reference trap; three parcel-ending cases).

## 19. Fix 7 — the table lane (born-digital) (3 Oct 2026)

**The problem.** Tables (land acquisition schedules, customs goods lists,
personnel lists, tariffs, exchequer and electoral tables) came out as
paragraphs. Each row's words survived, but **which value belongs to which row
and column did not**, so neither a template nor the AI could read a parcel
together with its owner and area.

**A stricter score first** (`tools/table_eval.py`). A printed row counts as
kept only if **one output line** holds the row and not much more (≤ 1.5× its
words + 3). The old score ("the row's words appear in order somewhere") passed
whole tables glued into one paragraph.

**Two referees, and why the second was needed.**
- **pdftotext -layout** was the referee at first. On 2024 No 89 p28 it shifted
  a parcel column by one row and paired every parcel with the next row's
  owner. The rendered page proved our pairing right.
- So the main referee is now **the page image**: Tesseract's word boxes,
  which already exist for every gazette (cells split at gaps > 2.5% of the
  page width, 80% of words for OCR's digit errors). It has its own quirk: it
  joins rows of two tables printed side by side.

**Lesson 45:** check the referee too. Score against two independent ones and
look at the page when they disagree.

**What was built.**
1. **`inspect_positions.js` writes cells.** On a baseline, a gap wider than
   1.5 em between pieces becomes ` | `.
   - A line with **≥ 2** wide gaps is a row.
   - A line with **one** wide gap is a row only inside a run of ≥ 3 lines whose
     cells start at the same x. A lone two-part line is a signature
     ("MR/4300204   Registrar …") and stays prose, so template patterns over
     it don't change.
   - **Justified prose is excluded.** A prose line holding few words is
     stretched, so every gap is wide and they are all equal; table cells sit
     at uneven distances. Without this, 21 land notices in 2023 alone lost
     their template ("district | of | Kirinyaga, | registered").
   - **Columns are learnt.** In a narrow column a long parcel number leaves
     less than 1.5 em before the owner. Column start positions are learnt
     from the rows with wide gaps (seen in ≥ 2 rows of the same page column)
     and every row is split there; neighbouring lines whose pieces start on a
     learnt column join the table.
2. **The cleaner keeps a row on its own line** (before the numbered-item rule,
   because rows often begin "1. | 233426 | …").
3. **Repeated headers across pages are dropped.** The running head marks the
   page break (`@@PAGE@@`). A cell row without digits that is the **first
   table row of a page** and repeats an earlier row of the same notice is the
   header again, so it is dropped. The first version dropped any repeat:
   899 rows, many of them data ("Ward Administrator | Ex-Officio Member" once
   per ward). Limited to page-first rows, it drops 287, all real headers.

**Results** (born-digital, against the page image):

| year | table rows | kept as rows, before | kept as rows **with cells**, after | cell count = image |
|---|---|---|---|---|
| 2022 | 3,348 | 2.4% | **59.6%** | 49.3% |
| 2023 | 3,535 | 1.1% | **59.9%** | 53.6% |
| 2024 | 5,067 | 0.3% | **40.4%** | 24.4% |
| 2025 | 53,809 | 11.7% | **81.7%** | 47.1% |
| 2026 | 5,017 | 0.8% | **65.5%** | 55.7% |

Probate cause lists reach 92–98%, and 2025 land schedules 87%.

**Prose is unchanged.** Same 21,250 notices, **0** category changes (Python
and Java), probate blocks and land rates identical in every year except one
2026 land notice ("in | Mwingi Sub-county, | registered" is still read as a
row). The Java cleaner (`@@PAGE@@`, row lines, `dropRepeatedTableHeaders`)
is identical to Python on all 29 born-digital 2024 gazettes.

**What is left: fix 7b, ruled tables.**
- In some ruled tables a row's cells are printed at different heights: the
  owner wraps over three lines and the area is centred, so no baseline holds
  the row (2024 No 203 p48). Only the ruling lines tell which cells belong
  together.
- pdf-inspector's `detectVectorGridInRegion` reads the grid and, filled with
  the positioned text, gives exact rows, multi-line cells included
  (`tools/grid_probe.js`). But it works only on the whole page, merges two
  side-by-side tables, and **invents grids on prose pages**: it reported a
  grid on 90% of table pages, including an 11-column "table" of two prose
  columns. It needs a reliable "real ruled table" test before it can be used.
- `extractPagesMarkdown` builds good pipe tables on full-width table pages
  but merges two page columns into one table, so it is not safe either.

**Lesson 46:** a library function's name ("detect grid", "markdown tables")
is a hypothesis. Run it on a prose page as well as on the case it was meant
for.

**Regression cases:** 3 in `audit.py` (rows keep their lines; a header
repeated at a page top is dropped; repeated data rows are kept).

## 20. Fix 8 — tables as data, shown on the notice page (3 Oct 2026)

**Goal.** Rows with cells are readable text. The next step is data:
`{columns, rows}` for every table, so the notice page can show a real table
(a land schedule as Parcel | Owner | Area, a committee as Name | Position).

**One generic extractor, not a template per table kind.** Tables appear in
every category: probate cause lists, county committees, company registers,
mining licences, land acquisition, tariffs, election schedules (1,081
notices). `tools/table_extract.py`, ported to Java as `TableExtractor`:
- a table is a run of cell rows;
- a short line between two rows (≤ 8 words, no sentence end) is a wrapped
  cell, appended to the row above ("the County Council (Example Coffee
  Nursery)");
- a headerless piece directly after a table of the same width is that table
  continued (page break, "(Contd.)"), so it joins it. This cut 7,468
  fragments to 3,468 tables;
- every row is padded to the header's width.

**Headers, without guessing.**
1. **Typeface.** pdf-inspector never sets `isBold`, but a bold face is
   embedded as its own font (header "Parcel No." in TT4, data in TT1). In
   each table the body font is the font of most cells; top rows set
   entirely in another font are the header. `inspect_positions.js` writes a
   `--- | ---` line under them, readable by the extractor and the AI alike.
   A header repeated at the top of a page is dropped together with its
   `---` line (cleaner, Python and Java).
2. **Words.** Some headers are in the body font ("Name | Position"). The
   words of the typeface-marked headers form a learnt vocabulary
   (`table_header_words.txt`, 185 words seen in ≥ 3 headers). A digit-free
   first row whose content words are ≥ 70% header words is a header;
   "Kipkelion | Kericho" and "Ward Administrator | Ex-Officio Member" stay data.
   The first rule I tried ("a digit-free first row is a header") merged the
   data row "Kipkelion | Kericho" into the header of a court list.

**Results** (born-digital 2022–2026):

| | |
|---|---|
| notices with tables | 1,081 |
| tables | 3,468 (from 7,468 fragments) |
| tables with a header | 33.5% |
| rows under a header | 35.8% of 117,469 |
| rows matching their table's width | 93.4% |
| Java `TableExtractor` vs Python | identical on 21,250 notices, ~0.2 ms each |
| categories / probate blocks / land | unchanged (0 changes, 96.0%, 93.7%) |

**Why most rows still have no header.** A few huge registers hold most of
them: a 3,919-row company register (2025 No 112) whose rows wrap onto a second
baseline, and the NCA contractor registers (2025 No 233 / 246) with
multi-line cells everywhere. The rows are there; the structure needs the
ruled-table work (fix 7b).

**On the notice page:** a **Tables (N)** tab with real HTML tables, built at
view time from the stored text. Huge tables show their first 300 rows and
say so. (Compiled; not yet viewed in a running app.)

**Lesson 47:** use the document's own signals before inventing heuristics.
The typeface marked headers more reliably than any rule about digits, and the
words of those headers taught the rule for the rest.

## 21. Fix 9 — table rows as records: land acquisition and its corrigenda (3 Oct 2026)

**Where the tables matter most.** National Land Commission notices list the
parcels to be acquired for a road or bridge, and their corrections list the
parcels **deleted, corrected and added**, one table per section. The
corrigenda template read 4 of 75 corrigenda (5.3%): these were the rest,
sent whole to the AI, and long ones were truncated.

**What was built.**
1. **Captions** (`table_extract`). The short line above a table is kept as
   its caption. A short line between two tables is decided only once the next
   line is known: if a header follows, it's the new table's caption
   ("Corrigenda"); otherwise it's a wrapped cell of the row above. The first
   version glued "Corrigenda" onto the previous owner's name. Only a
   **section word** (Deletion, Addendum, Corrigend…, Schedule, Part, Annex)
   stops a continued piece from merging; any short line did at first, and
   that undid the merging (3,468 → 5,800 tables).
2. **Column roles** (`tools/table_records.py`). Header words map to roles:
   parcel_id, old_lr / new_parcel, owner, area_ha, name, position. 526 headed
   tables have roles: 355 are committee lists (name / position), 50 are
   registration-unit conversions, 50+ are parcel schedules.
3. **Print defects repaired:**
   - two records on one line (exactly twice the header width) become two rows;
   - an owner cell that was never printed: the area slid into it and is moved back;
   - an area glued onto the owner ("TBD 0.0107") is split off;
   - "Tetu/Unjiru/ 1926" is closed up.
4. **Validation.** A parcel id has a digit, no area-like decimal, at most 6
   words, and at most 2 words after its last number. So "Busia/Magombe/752
   0.0017 John …" (a whole row in one cell) and "Kiganjo/Kiamwangi/2510 Hana
   Jane Roe" (owner glued on) are refused. Refused rows are left out
   and counted (`rows_not_read`), never guessed.
5. **`tools/land_table_template.py`** returns a subtype (compulsory
   acquisition / correction of an acquisition schedule / conversion of L.R.
   numbers), the project, the acquiring body, the earlier notices it amends,
   and sections of parcel records. It is only used when ≥ 80% of the rows are
   valid. It is wired in after the existing land and corrigenda templates.

**Results** (born-digital 2022–2026):

| | before | after |
|---|---|---|
| corrigenda templated | 4 of 75 (5.3%) | **21 (28.0%)** |
| land notices templated | 8,285 | 8,301 (+16; 93.3%) |
| parcel records from these notices | 0 | **2,148** (rows not read 117, 5.2%) |

All 33 newly templated notices were read line by line. Two review rounds
removed the glued-row cases; the remaining "not read" rows are left out
visibly.

**Not yet in Java.** All templates (probate, land, corrigenda, now land
tables) exist only in Python, the measuring side. Moving them into the
deployed Java service is the open item with the most production value:
probate 96% and land 93% of notices would skip the AI call.

**Lesson 48:** let a template refuse. A strict validity test plus a count of
what it did not read is better than a complete-looking record with a glued
name in the parcel field.

**Regression cases:** 2 in `audit.py` (sections, related notices, missing
owner, split parcel, a glued row refused; glued-owner parcel test).

## 22. The templates in the deployed app (Java) (3 Oct 2026)

**Your decision:** port the templates to Java, rather than have Java call
Python. One runtime in production; Python stays the measuring lab.

**What was ported** (package `service.templates`, ~800 lines):

**The traps of a regex port, and what each needed:**

| Python | Java |
|---|---|
| `\s \w \b \d` are Unicode-aware | `UNICODE_CHARACTER_CLASS` |
| `.` and `$` know only `\n` as a line end | `UNIX_LINES` (Java also treats `\r`, ` ` … as line ends) |
| group names like `case_ref` | no underscores allowed: `caseRef` |
| `s.strip(' ,.')`, `str.title()`, `split()` | written out exactly in `Py` |
| `split_causes` hides "(Formerly CAUSE NO." with a **non-breaking space** | the same ` ` trick |
| `'%s' % None` prints `None` | reproduced where it reaches the output |

**Parity:** Python and Java records **identical on all 16,860
probate / land / corrigenda notices** of 2022–2026, on the first run.

**Wired into the pipeline** (`GazetteService`):
1. **Single notices:** a template result replaces the AI extraction call;
   only the article call remains.
2. **Multi-cause probate notices:** the template reads the **whole** notice,
   because the court and the objection deadline are printed once. When it
   reads every cause and the count matches the Java chunks, record *i* is
   sub-case *i*. That covers 83.2% of the 4,811 multi-cause notices. The
   others go cause by cause, still trying the template first.
3. **Batched land notices:** the batch call (extraction and article for five
   notices in one call) is kept because it is cheaper, but where a template
   reads a notice, **its exact fields replace the AI's extracted fields**.
4. **Safeguards:** a template error falls back to the AI path. A parcel
   schedule sends only its first 20 parcels per section, plus counts, to the
   article call; the stored record keeps everything.

**The unit tests found two real gaps** — in Python too, unseen until now
(`NoticeTemplatesTest`, 8 tests on real notice shapes with names replaced;
they run in any CI build without the private corpus):
1. **"for a grant of probate of written will *to the estate of* X"**: the
   pattern allowed "will of" or "to the estate of", not both. That was
   **285 cause blocks, none read**. Fixed in both languages: probate notices
   fully templated 6,763 → **6,818 (86.4%)**, cause blocks **96.5%**.
2. **Probate corrigenda never had `amends_notice`.** The corrected notice is
   named before the CAUSE NO., but only the cause block was searched. The
   whole notice is now searched, minus its own header line: the first
   version of the fix picked up "GAZETTE NOTICE NO. 2", the corrigendum
   itself. A test caught that too.

**Lesson 49:** a test written from a real document shape tests the rule as
well as the port. Both gaps lived in Python for weeks; the Java tests found
them on their first run.

**Effect in production** (expected, from the corpus figures): for about 86%
of probate notices, 93% of land notices and 28% of corrigenda the
extraction call is replaced by an exact template result. Those notices
still get one AI call to write the article.

**Not run here:** the deployed app end to end (database, AI keys). The
Spring `contextLoads` test needs the database.

## 26. Fix 7b — ruled tables, rebuilt from the printed lines (4 Oct 2026)

**The problem.** In a ruled table a cell can wrap onto several lines. A row
then has no single baseline, and today's extractor broke it apart:

```
Siaya/Sumba/3291 | SC 9            <- the owners and the area are missing
...
Doe | Roe, | 0.0485          <- orphan pieces of other rows
```

**The first tool was a false start.** pdf-inspector's
`detectVectorGridInRegion` sounds like the answer. It is not:
- it finds a grid only for a whole page (any crop returns nothing);
- its column walls are not the printed ones;
- its row walls sit on text baselines, and on prose it draws one "row" per
  line.

It derives its grid from the text, so it cannot tell a table from prose.
(Lesson 46 again: a function's name is a hypothesis.)

**The real witness is the printed lines.** Poppler's `pdftocairo -svg` (already
used by the scan lane) exposes the page's drawing commands. `pdf_rules.js`
reads the rules from them:
- on p48 the five true column walls;
- a taller row around a two-line owner cell.

Prose has no rules, so it is never touched. You approved making poppler part
of every extraction.

**How it works** (`inspect_positions.js`, the one extractor Python and Java
both run, so the extraction itself needs no Java port):
1. **Lattices.** At least 3 walls, at least 3 rules, and text inside.
2. **Cells.** The text inside a lattice leaves the normal layout and goes
   into cells. A text item running across a real wall is split at the
   nearest space.
3. **Rows.** One row per band between rules, `" | "` between cells, the
   header marked by its typeface as in fix 8.
4. **Placement.** The table's rows are placed back where the table sits.
   Pages without a lattice are byte-identical.

**What the checks found.** The checks caught every problem below, each one
before the commit:

| check | what it found | fix |
|---|---|---|
| word check | "3rd" printed as "3" + raised "rd" read as "3" … "rdKENAS" | group a cell's pieces into baselines first |
| word check | "Gender Year " + "of" read as "Yearof" | split pieces keep the space they were cut at |
| visual review | a date in the address cell: the cut point was estimated by counting characters in a line of capitals | estimate with typical letter widths |
| visual review | a cell merged downwards collapsed three sub-rows into one ("2,500 7,500 10,000") | each column keeps its own rules |
| template losses | a prose notice scrambled: the rule printed *between page columns* was taken as a table wall | that rule is not a wall; a "table" whose rows hold one cell is not a table |
| template losses | a one-row table lost its header mark; date rows merged across the table broke it into pieces; one-row groups lost their walls | body font from the rows below the header; `"label |"` rows; walls ≥ 6 pt; a one-cell label is not a record |
| parity | Python squashed `"a |  | c"`, Java did not | the extractor writes `"a | | c"` |

**Results** (260 born-digital gazettes and the held-out issues):

| measure | result |
|---|---|
| pages with ruled tables | 1,890 (26%): 199,815 lines → 121,056 rows |
| characters on those pages | **identical** (0 of 1,890 differ): text only moves |
| rows at their table's width | 96,771 → **110,049** |
| notices / templates | 20,977 → 20,978 (a lost notice found); templates **+39, 0 lost** |
| held-out No 166 | rows at width **54% → 98%**; templates 217 → 219 |
| an inquiry schedule (2025 No 93) | 111 parcels with areas (was 43 without) |
| Python = Java | tables 20,978/20,978, templates identical, cleaner 89/89 |

**Lesson 53:** the strongest no-loss test was the simplest. The *characters*
of a page must not change, only their order and spacing. It turned "are
these word differences bad?" from a judgement into a fact (0 of 1,890
pages), and the visual review and the template losses then found what that
test cannot see: text in the wrong cell or the wrong row.

## 27. Tables in scanned gazettes (4 Oct 2026)

**The starting point.** 220 of 1,167 scanned pages carry tables: company
registers, customs lists, election results, cause lists, exchequer tables.
Tesseract reads a table row as a line, but three things go wrong:
- the column rules become characters ("1319] PVT-6LULKE2X __| King …");
- the cells run together;
- a rule read as `" | "` becomes our cell marker. That made **4,169 lines of
  fake cells**, and "tables" in 51 notices that were really splits at rule

**The approach mirrors fix 7b on paper instead of vectors.** The ruling
lines are found in the page image: long dark runs, joined across small gaps
and a slight skew, found in 0.16 s a page. The rows and cells are then
rebuilt from Tesseract's word boxes. Two foundations were checked first:
- rebuilding a page from the word boxes gives exactly Tesseract's text (90
  of 90 pages), so a page without tables is unchanged;
- letters and digits are compared on every page.

**What the review found** (each fixed before the commit):

| found by | problem | fix |
|---|---|---|
| reading the rows | words in a cell scrambled; rows slipping by one | order by Tesseract's own lines; lighter threshold for thin rules |
| a real scan (2022 No 169) | faint rules lost → five counties in one row | where a band holds several key entries, one row per printed line, nothing joined (cells are vertically centred, so any join would be a guess) |
| the notice count | "GAZETTE NOTICE NO. \\| 2057" (a 1 read as a bar): dropping the bar lost notice 12057 | a bar before a number stays, glued to it, for the number repair |
| review | prose beside a table read as table rows (2024 No 6) | an unruled cell may be at most a third of the page wide |

**Results:**

| measure | result |
|---|---|
| letters and digits | identical on 1,167 / 1,167 pages |
| fake cells | 4,169 → **0** |
| table rows | 7,253 ruled (wrapped cells joined) + 2,745 unruled |
| notices found | 3,842 → **3,846** of 3,982 printed; probate +6, land +2 |
| Python = Java | 1,167 / 1,167 pages; rules 40 / 40 images |

**Lesson 54:** when the evidence for a decision is missing, say so in the

order, so the marker travels with the text into its notice — the same way a
table cell keeps its row. That is how a party symbol stays with its
candidate.

**What each image is.** Rules, in order, using size, place, the text on the
image and the notice around it. Your decision mattered here: *keep
everything* — a stamp can be the authentication — so nothing is thrown away;
the kinds only decide what is shown with the article and what is listed as
"other images". Reviewing the kinds found 7 misreadings, each now a rule
(a KRA chart called a map because its tables say "KAA Concession Fees"; a
one-row statement strip called a logo; a printed form called a map).

**Reading the text on an image.** You asked whether RapidOCR would do better
than Tesseract here, where speed matters less. Measured on the 241 images
that carry text: map titles that match their notice went from 45 to 129, and
Tesseract got amounts wrong on a statement (9,224,208 for 3,224,208). Then
the harder part — Java production:
- the Java library you approved (a wrapper around RapidOCR's C++) **dropped
  every space** ("NAIROBIBLOCK21"): worse than Tesseract on maps;
- so I ported RapidOCR's own pipeline to Java (`service.PpOcr`, ONNX
  Runtime, the same PP-OCRv6 models);
- ONNX Runtime 1.21+ crashed at start: this JDK carries an older Visual C++
  runtime (pinned 1.20.0, which works);
- the spaces were *still* missing. Comparing Python and Java frame by frame
  on one image showed the model *did* predict the space — Java's character
  list was 540 entries short, because ONNX Runtime's Java binding decodes the
  list stored in the model as "modified UTF-8" and breaks the rare 4-byte
  characters at its end. The space is the last entry. Fix: the list is a
  UTF-8 file, and the code checks its length against the model's output.

Result: the Java port reads map titles almost as well as Python (124 vs 129
of 205) in half the time, and the image kinds do not change.

**Cleaner copies, honestly.** The cleanup divides by a blurred copy of the
page (removes the brown), stretches contrast and sharpens. Every pixel comes
from the original's own neighbourhood; nothing is invented. The original is
always kept and one click away — the stretch also darkens old stains, which
you can judge on 2022 No 43.

**On the site.** A "Figures (N)" tab on the notice page (cleaned ↔ original
toggle, the text read on the image, "other images" for logos and stamps), and
the images appear in place in "Original notice text". Tested in the running

**Found on the way:** your `application.properties` still pointed the app at
the old `pdftools/scripts/inspect.js` — the running app was not using the

**Lessons 56–57:** a library's promise is a hypothesis — measure it on your

## 30. The law library — what each notice rests on (4–5 Oct 2026)

**You asked:** keep the laws notices refer to in the system, like the
counties, and let the article quote and explain them.

**First, how notices use laws.** Only 7.6% cite a section ("section 36 of
the Universities Act"). Almost half name an Act only in their heading —
8,614 of them the Land Registration Act. So most of the value is not in
parsing citations but in knowing *which section a kind of notice is issued
under*.

**Getting the laws.** Kenya Law's terms forbid bulk downloading, so you saved
the 40 most-named Acts yourself (thank you). They came as PDFs, not the web
pages the builder read, so a PDF reader was built (`tools/law_pdf.py`): the
Contents page lists every section number and title in order, so each section
is found by looking for the *next expected* heading — never by guessing from
any line that starts with a number. 39 Acts came out complete (the Companies
Act alone has 1,033 sections); the one scanned edition (EAC Customs
Management Act) 215 of 225. Each file keeps its "text as at" date.

**Which section a notice is issued under.** Reading the notices next to the
Act made it exact: a lost title deed → s.33(3) (Gazette notice, sixty days);
a lost register / green card → s.33(5); "I intend to dispense with the
production of the title" → s.31(1). These are rules in a data file
(`reference/implied.json`), each written down with the words of the section
that justify it. A random check of 30 notices: 30 right. Notices about a
lost *grant* (an older kind of title) were left alone — s.33 speaks of
certificates, and a guess about the law is worse than no link.

**Results:** notices with a law link 1,682 → 11,297; the "Laws" tab labels
each link honestly (cited / "the section this kind of notice is issued
under" / named in the notice) with its version date and a Kenya Law link.
The article ends with a fixed sentence quoting the law from the stored text,
and an AI may explain the law only within LAW CONTEXT — any quotation it
writes is checked word for word and removed if it is not in the law.

**Found on the way:** a Java string written `"\s*"` (one backslash) instead of `"\\s*"`
compiles without complaint — since Java 15 `\s` means a space — and the
resolver silently matched nothing. The Python-vs-Java parity run caught it
(19,577 of 21,250 identical → fixed → 21,250). `audit.py` now scans every
Java string for single-backslash regex escapes (`\s \d \w \b`).

**Lesson 58:** most of the meaning is in the *kind* of notice, not in what it
cites; and for law, an unmatched notice is better than a wrong section.

## Glossary

- **Text layer** — the text embedded in a PDF (exact for born-digital PDFs; a hidden OCR guess for scans).
- **Born-digital vs scan** — produced from a word processor vs photographed/scanned paper.
- **LIS (longest increasing subsequence)** — the largest set of items, in document order, whose values strictly increase; used to keep real notice headers and drop out-of-place cross-references.
- **Precision / recall** — of the notices a keyword fires on, how many are right / of the notices it should catch, how many it does.
- **F1** — the balance of precision and recall (used for word overlap).
- **Held-out set** — data kept aside and only used to test a finished change.
- **Regression test** — a saved example that must keep passing after future changes.
- **ONNX / ONNX Runtime** — a portable format for machine-learning models and the engine that runs them (has a Java API).
- **oneDNN** — Intel's CPU acceleration library used by PaddlePaddle; the source of the crash.
- **Quadratic** — run time grows with the square of the input; 10× more text → 100× slower.
